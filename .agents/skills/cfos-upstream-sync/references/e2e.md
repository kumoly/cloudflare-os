# CFOS upstream sync and acceptance

1. Inspect `git status`, remote identities and push URLs, `.cfos/stack.json`, the installed `config/runtime-version.json`, and the scan result. Pin the exact upstream head. Use an isolated worktree based on the current `cfos/main`; never edit the running installation checkout. Preserve a local backup ref before any history rewrite.
2. Bring upstream commits into a candidate branch. Prefer the user's requested merge or rebase method. A rebase changes downstream commit IDs; do not force-update a protected/shared branch without explicit authorization and a verified old SHA. Keep compatibility commits and update `.cfos/stack.json` to the tested upstream base. Resolve conflicts using the intended final source tree, then review the resulting diff and commit ancestry.
3. Run the repository publication guard and privacy scanner before a public push. Run focused affected tests, `pnpm lint`, `pnpm test`, and the build required by `docs/cfos-development.md`; test the changed capability against an isolated copy of state and the existing local CFOS instance as appropriate. Record the exact candidate SHA and checks. Do not treat a green tree-equivalent commit as proof that a different SHA's CI ran.
4. Push the candidate and require public CI on its exact SHA. Open a PR into protected `cfos/main`. If a rebased candidate conflicts with old protected history, a separate PR bridge commit may connect the old tip as a second parent while retaining the validated candidate tree; verify both parent SHAs and tree equality, then run publication checks and CI again on the bridge SHA. This PR path retains both histories. An exact rebase of `cfos/main` instead requires the owner's explicit one-time authorization and branch rules that permit an old-SHA-checked force update.
5. Merge the PR only when authorized and its required checks pass. Verify the resulting remote `cfos/main` SHA and public CI for that exact SHA. Fast-forward the local integration checkout. Confirm its tree matches the tested source.
6. Refresh the local installation through `~/services/cloudflare-os/config/cfos-local.mjs` or the documented backed-up full deployment path according to the plan. Keep host configuration and data outside the fork. Restart the LaunchAgent if needed, then verify `config/doctor`, login and workspace persistence, and acceptance for the changed capability. Record the integrated SHA, tree, CI URL, backup or rollback path, and acceptance results in the host receipts. If a local check fails, use the saved rollback path and verify the restored service.
7. Report what changed, what is actually enabled locally, test and CI evidence, any outstanding limitation, and a small Git parent graph showing `upstream/main`, `origin/main`, candidate, PR bridge if present, and `origin/cfos/main`.

The repo's development guide and the user's current authorization govern specific commands and publication permissions. A scheduled scan never enters steps 1–7.
